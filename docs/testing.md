# Testing

How the STM32 target is checked. The layers follow the RISC-V target, which
was checked with riscv-tests, NuttX ostest, trace comparison with another
implementation, and a decoder cross-check.

## Status

What is in place on 2026-11-04 and what is planned. "CTest" means it runs
with `(cd build && ctest)` (36 tests, all passing on macOS and WSL2);
there is no CI workflow in this repository yet.

## 1. Toolchain (Docker)

All test programs and firmware are built in one Docker image,
[docker/Dockerfile](../docker/Dockerfile): PX4's own build image
(`px4io/px4-dev:v1.17.0-beta1`, with the Arm GNU toolchain `arm-none-eabi-gcc`
13.2 that PX4 uses for Pixhawk) plus the reference tools (QEMU's Cortex-M7
machine `mps2-an500`, llvm-objdump). PX4 `px4_fmu-v5`, NuttX for the ostest
and the hand-written tests all use the same compiler.

```bash
docker build -t athrill-stm32-toolchain docker/
```

Renode joins the image once its Linux package for the host architecture is
checked.

## 2. Instruction set

There is no freely usable official Armv7-M test suite (Arm's compliance kit
is a licensed product), so three kinds of tests are combined:

| Kind | Content | Reference |
|---|---|---|
| Self-checking programs | Per instruction class: results, flags (N, Z, C, V, Q, GE), exceptions; floating point with rounding modes and exception flags. The same form as the RISC-V target's self-tests | Arm's architecture reference manual |
| Generated instruction tests (in use) | One instruction per case with random operands from a fixed seed; all registers (and the memory a store wrote) printed after it and compared with the same program's output on QEMU (below) | QEMU `netduinoplus2` / `mps2-an500`, used as an external tool |
| Random instruction sequences (planned) | Random Thumb-2 sequences run from the same initial state on Athrill and on the reference; registers and memory compared after each instruction | QEMU `mps2-an500` (Cortex-M7), used as an external tool |
| Decoder cross-check | Every 16-bit encoding and sampled 32-bit encodings disassembled and compared (design decision 10) | GNU objdump, llvm-objdump |

### Instruction tests in use

`test/insn` has one program per group of instructions. `insn.S`, `dp.S` and
`dp2.S` are written by hand (ADD/LDR/B, data processing); `ls.S` (loads and
stores), `br.S` (branches), `mx.S` (SP-relative ADD/SUB, ADR, MOVT,
extend, bitfield, bit operations, multiply and divide), `sy.S` (IT blocks,
MRS/MSR, barriers, hints), `dsp.S` (DSP extension, with GE and Q read back
by MRS), the floating-point groups (`fpm.S`: moves, VMRS/VMSR, loads and
stores; `fpa.S`: arithmetic and compare; `fpc.S`: conversions, round to
integral, VMAXNM/VMINNM) are generated by `tools/generate_insn_tests.py`
from case templates with random operands (fixed seed): every case sets
r0-r6, r8-r12 and LR to random values, runs one instruction and prints all of
them (and the memory a store wrote), so a wrong result or a register changed
by mistake shows.

`test/insn/build.sh` builds each program twice, for this target (STM32F7
USART) and for QEMU's `netduinoplus2` (STM32F4 USART, a Cortex-M4 whose
Armv7-M integer instructions mean the same), with the same instructions at
the same addresses but for the USART register offsets; the QEMU run's output
is kept as `<test>.expected`. CTest (`insn-<test>`, `test/insn/run.sh`) runs
the program on Athrill and compares its output with that file line by line.
The expected values thus come from an implementation independent of Athrill
and of whoever writes the test.

`tools/check_insn_tests.py` lists the encodings with an executor that no test
program contains; there must be none.

## 3. Coverage

`tools/coverage.sh` builds the target with clang's source-based coverage,
runs the CTest tests and reports:

- code coverage (regions, functions, lines, branches) of the executors, the
  glue, the M-profile implementation and athrill-arm-common's pseudo-code;
- encoding coverage: of the encodings with an executor, which the tests run
  (`tools/encoding_coverage.py`); with `--usage` and the output of
  `tools/insn_usage.py`, also the share of a firmware's start-up that has an
  executor and that is tested.

The aim is every encoding with an executor run by a test. Branches that only
an UNPREDICTABLE encoding takes are not counted against it. athrill-arm-common
measures its pseudo-code by its own unit tests (`tools/coverage.sh` there).

## 4. Exceptions and interrupts

The stacked frame on exception entry, priorities and preemption,
tail-chaining, lazy floating-point stacking, SysTick, PendSV, SVCall and
exception return (EXC_RETURN): `exc.S` ("Exception test" below), compared
with QEMU. A comparison with Renode is planned.

## 5. The whole chip: Renode (planned)

Renode models the STM32F7 with its peripherals. The same firmware runs on
Athrill and on Renode, and their behaviour is compared: peripheral register
sequences, NuttX and PX4 boot logs and, with execution traces, the
instruction stream up to the first difference. Renode is used as an external
tool only (design decision 8). The same runs also compare the speed of the
two.

## 6. Operating systems

- PX4 `px4_fmu-v5_default`, as built, boots to the NSH prompt and flies
  SIH (done; [verification](verification.md)).
- NuttX ostest on an STM32F7 board configuration of NuttX (for example
  Nucleo-F767ZI), with the NuttX version PX4 uses, to run to the end and
  pass (planned).
- ChibiOS tests with ArduPilot (planned, stage 3).

## 7. Peripherals and sensor chips

In CTest (`test/device`): the timers, the UARTs (with receive DMA), SPI with
the MS5611, DMA with the ICM-20689, I2C with the IST8310, the u-blox GPS,
the F-RAM and the SDMMC with the SD card. Unit tests per peripheral against the STM32F7 reference manual: register
reads and writes, status bits, interrupts, DMA transfers. Sensor chips: the
registers their PX4 drivers use (identification, setup, data-ready, data).
The same form as the RISC-V target's UART and timer unit tests.

## 8. Rules carried over from the RISC-V target

- Every speed-up gives byte-identical output to one-instruction-at-a-time
  execution.
- Athrill can write an execution trace (with the virtual clock) for
  comparisons with other implementations.
- All tests run automatically (CTest); running them in CI is planned.

### Floating-point tests

The floating-point groups need double precision, which QEMU's netduinoplus2
(a Cortex-M4) does not have: their expected output comes from QEMU's
mps2-an500, a Cortex-M7 with FPv5-D16. The same source is built for it
(`-DTARGET_AN500`: its CMSDK UART, the CPACR write that enables its FPU,
`link_an500.ld`) and for the STM32 target. The two builds are at different
addresses, so these tests print no address: each case prints r0-r3, FPSCR,
APSR and S0-S31 (and its store slot), starting from one of 16 sets of S0-S31
with zeros, infinities, NaNs and denormals among them, and from an FPSCR
with a random rounding mode, FZ, DN (and AHP for the conversions). Half of
the arithmetic and conversion cases set their operands explicitly: values
close to each other (cancellation, ties), close to integers and halves (the
conversions' rounding), and directed cases for exact ties, FMA's quiet NaN
with infinity times zero and square roots whose remainder decides the
rounding.

### Exception test

`exc.S` is written by hand: each part is a situation of the exception model
rather than an instruction with random operands. All vectors lead to one
handler that logs, per exception, IPSR, EXC_RETURN, the frame's address,
the stacked R0, PC and xPSR, CONTROL and CFSR; a scenario puts an action in
a table the handler calls for an exception. The scenarios: SVC with an
unaligned stack, PendSV and SysTick by ICSR, interrupt priorities with a
nested and a tail-chained interrupt, PRIMASK (with WFI not waiting),
BASEPRI and BASEPRI_MAX, PRIGROUP, the process stack, unprivileged Thread
mode, UsageFaults (UDF, division by zero) and their escalation to HardFault,
INVSTATE, an illegal EXC_RETURN (INVPC), SVC escalated from a handler, the
floating-point context preserved lazily or left, equal priorities, the
hints and BKPT. Its reference is QEMU's netduinoplus2 like the integer
tests (same addresses: the stacked PCs are compared). FPCCR is printed
without bit 10, which QEMU sets (SFRDY of Armv8-M), a reserved bit of
Armv7-M.
